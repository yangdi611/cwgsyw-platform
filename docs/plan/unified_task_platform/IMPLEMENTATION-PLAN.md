# 统一任务平台实施计划

**状态：** 待开始  
**实施模式：** 高风险保护模式、按工作包顺序推进  
**数据前提：** 保护现有数据库和 V1-V79 历史；旧日报、旧 `ops_schedule_*` 和它们的专属关联物已明确删除，其他正式业务模块对象保持不变。  
**禁止：** 长期兼容层、双写、双读、半完成旧接口清理

---

## 1. 总体策略

本项目涉及任务、工作流、CMDB、通知、权限、数据库和多个前端入口，不适合一次大爆炸式无检查改动。代码可以在一个长期实施任务内持续完成，但必须按工作包形成可验证检查点。

原则：

1. 先建立新模型，再接入用户路径，最后删除旧模型。
2. 同一工作包内保持 schema、后端、前端和测试契约一致。
3. 中间阶段可以在开发分支中存在尚未导航暴露的新功能，但不得把旧/新双入口作为最终交付。
4. 旧实现删除只有在所有内部消费者切换后进行。
5. 每个工作包开始前执行 GitNexus query/context/impact，结束后执行定向测试和 `detect_changes`。
6. 每次更新 `IMPLEMENTATION-STATUS.md`，记录文件、命令、结果和下一步。

## 14. 每个工作包的标准执行循环

```text
1. 读取状态和本工作包文档
2. 检查 git status
3. GitNexus query/context
4. 对每个拟编辑 symbol upstream impact
5. HIGH/CRITICAL 告警并重新核对边界
6. 编写/更新定向测试
7. 实施最小完整切片
8. 运行定向测试
9. 运行 compile/typecheck/lint
10. GitNexus detect_changes
11. 更新 IMPLEMENTATION-STATUS.md
12. 进入下一工作包
```

## 15. 提交与回滚建议

如用户授权提交，建议每个工作包至少一个独立提交，schema 与对应最小运行代码不得分离到导致任一提交不可启动的状态。

回滚：

- 代码使用工作包提交回退。
- 数据库回滚依赖升级前备份；已执行 migration 不修改、不 repair，修复使用下一递增版本。
- 不保留旧运行时 API 作为回滚手段。

## 16. 范围变化规则

- 发现阻塞实施的必要工作可加入当前工作包，但先更新本计划和状态文档。
