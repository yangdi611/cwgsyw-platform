# 前端页面统一化验收标准 v1.0

## 1. 验收结论

| 结论 | 标准 |
|---|---|
| 通过 | 所有 P0 通过，P1 无未解释失败，P2 有明确台账 |
| 有条件通过 | P0 全部通过，P1 仅有已授权且不影响核心使用的问题 |
| 不通过 | 任一 P0 失败，或出现行为回归、权限绕过、数据错误、页面不可用 |

## 2. P0：阻断项

### P0-01 行为合同不变

- 路由、动态参数、重定向和面包屑仍可用。
- API 路径、HTTP 方法、query key、分页和筛选参数未改变。
- 权限不足仍被正确阻断；隐藏按钮不等于放宽后端权限。
- 列表到详情、编辑、保存、返回的核心闭环可完成。

### P0-02 全局 Shell 可用

- 首页、CMDB、Workflow、Wiki 和一个无权限路由均可进入。
- 不出现首屏空白、双滚动条、Header 遮挡主内容或 Sidebar 覆盖内容。
- 390px 宽度下主要操作不被截断或隐藏到无法发现的位置。

### P0-03 状态完整

每个改造页面都验证：

- loading：不会因异步内容造成明显布局跳动。
- error：有可理解的错误和重试/返回路径。
- empty：说明当前没有数据的原因，并提供清除筛选或新建入口（适用时）。
- permission denied：不泄露业务数据或内部 ID。

### P0-04 特殊工作区不回归

- 拓扑、BPMN、Wiki 图谱、空间布局、文件预览和模板设计器仍能加载并交互。
- 画布页不被普通 `max-w-*` 限制。
- 工具栏、面板和画布没有互相遮挡。

## 3. P1：重要项

### P1-01 标题与操作

- 标准列表使用统一 PageHeader。
- 详情和表单有明确返回入口。
- 主操作位于稳定区域，危险操作使用一致确认语义。

### P1-02 列表语言

- 筛选栏、批量工具栏、表格行高、状态 Badge、分页和空态在同类页面一致。
- 表格保留业务列和权限差异，不强制把高密度审计页卡片化。

### P1-03 详情与表单语言

- 状态、更新时间、保存中和校验错误位置一致。
- 表单在桌面、平板、手机不发生横向溢出。
- 未保存离开行为保持原逻辑或明确提示。

### P1-04 无障碍

- 图标按钮有 `aria-label` 或 `title`。
- Dialog 有标题，打开后焦点可达，关闭后焦点回到触发控件（适用时）。
- 表单 label 与控件关联，错误提示可被读屏识别。
- 键盘可完成筛选、打开 Dialog、关闭 Dialog 和主要操作。

## 4. P2：收口项

- 新增代码不引入新的裸 `<h1>` 页面标题、固定 overlay、原生 table 或旧 Button 用法，除非记录例外原因。
- 颜色、圆角、边框、间距使用 V2 token 或既有设计系统。
- 低频页面与模块专用布局在文档中有明确保留理由。
- 静态扫描结果不比基线扩大未治理模式。

## 5. 验证矩阵

| 维度 | 桌面 | 平板 | 手机 |
|---|---|---|---|
| viewport | 1440x900 | 1024x768 | 390x844 |
| 主题 | 浅色，深色（若应用支持） | 浅色 | 浅色 |
| 页面 | 首页、列表、详情/表单、特殊工作区 | 首页、列表、详情/表单 | 首页、列表、详情/表单 |
| 操作 | 筛选、分页、主操作、Dialog、返回 | 同左，检查折叠 | 主操作、返回、滚动、溢出 |

## 6. 最低命令门禁

命令以仓库实际 `package.json` 为准，至少覆盖：

```bash
git diff --check
cd frontend && npm run lint
cd frontend && npm run typecheck
```

如存在对应脚本，继续运行：

```bash
cd frontend && npm run build
cd frontend && npm test -- --runInBand
```

必须在报告中区分：本次失败、基线失败、环境阻塞和未执行，不得用“未验证”写成“通过”。

## 7. 视觉证据要求

每个工作包至少保留：

- 一个普通列表页截图。
- 一个详情或表单页截图。
- 一个特殊工作区截图（若工作包涉及）。
- 1440x900、1024x768、390x844 中至少覆盖目标页面的实际尺寸。

截图需要证明：标题、主操作、状态、文本、表格/画布和滚动边界没有重叠或遮挡。只打开页面源码不能替代视觉验收。

## 8. 证据等级与阻塞规则

验收记录必须注明证据等级：

| 等级 | 最低内容 | 结论边界 |
|---|---|---|
| L0 | 源码、静态扫描 | 只能说明实现结构存在 |
| L1 | lint/typecheck/build/HTTP | 只能说明构建或服务可达 |
| L2 | 授权登录后的真实点击 | 可证明路由、权限和业务操作路径 |
| L3 | L2 加三种 viewport 的截图或等价检查 | 可证明本工作包的响应式运行时验收 |

缺少登录态、浏览器自动化、业务数据或外部授权时，记录 `BLOCKED`，不得用 L0/L1 替代 L2/L3。若用户同意延后，必须记录为 `DEFERRED`，包含授权人、原因和重新验收触发条件。

工作包状态与验收结论的关系：

- `VERIFIED`：退出条件所需的最低证据等级全部通过。
- `IN_PROGRESS`：仍有实施或证据工作未完成。
- `BLOCKED`：外部条件连续阻塞，当前无法完成。
- `DEFERRED`：用户明确批准暂缓，并有后续触发条件。
- `NOT_RUN`：尚未执行，不能解释为通过。
